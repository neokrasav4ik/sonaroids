# Sonaroids — переходная записка

Состояние на 24 сентября 2026. Рабочее название проекта — Sonaroids (sonar + asteroids); имя «Sonaroid» занято, окончательное название не выбрано (варианты — в разделе 9).

---

## 1. Что это и в каком состоянии

**Идея.** Веб-игра для iPhone без касаний. Телефон лежит горизонтально на столе, ладонь держится сбоку от короткого края телефона — со стороны микрофона. Высота ладони над столом двигает корабль по вертикали, корабль летит между астероидами. Измерение — ультразвуковой сонар на встроенных динамике и микрофоне: телефон непрерывно излучает неслышимый зонд и по его эху вычисляет высоту ладони.

**Состояние — работает.**
- Одна рука, точность высоты в игре: шум на экране около 1,5 мм, крупные скачки до 2–3 мм, рука видна 100% времени партии.
- Подготовка без калибровки (пустая комната сама, середина поля — по ладони), игра с тремя уровнями сложности, журнал партии для разбора, «Запись для меня» для проверки механики по метке.
- Запускается как веб-приложение с домашнего экрана iPhone — на весь экран. Пользователь выкладывает файл на свой хостинг под именем `sonar_lab3.html`, иконка на домашнем экране указывает на этот адрес, поэтому имя файла менять нельзя.

**Решено окончательно:**
- только одна рука — Safari отдаёт один микрофон, две руки не разделяются (раздел 4);
- телефон лежит на твёрдой опоре — на коленях и в руке не проверялось, по физике ожидается хуже (раздел 8);
- терменвокс удалён, развитие идёт через игру;
- паузы от убирания руки убраны: без руки корабль стоит на месте, старт и перезапуск — только кнопками;
- беззвучный режим телефона глушит зонд, и обойти это из браузера не удалось (раздел 3).

## 2. Как устроено

Исходники разложены по частям в `src/`, `build.py` склеивает их в `app/sonar_lab3.html`. Порядок частей важен: 00 и 01 открывают страницу и `<script>`, 02 и 03 — модули верхнего уровня (`DSP2`, `Game`), 04–09 — одна общая обёртка `(function(){ … })()`, которую закрывает 09.

| часть | что внутри |
|---|---|
| `00_head.html` | разметка, стили, все экраны, мета-теги веб-приложения, иконка (PNG в base64) |
| `01_worklet.js` | AudioWorklet `cap`: отдаёт кадры микрофона по 512 отсчётов подряд с порядковым номером |
| `02_dsp.js` | движок обработки `DSP2` — весь расчёт высоты и присутствия руки |
| `03_game_core.js` | логика игры `Game` без рисования — её можно гонять в node |
| `04_audio_engine.js` | звук: сессия, микрофон, генерация зонда, выбор канала, сигнал/шум, автоуровень, единая точка приёма кадров |
| `05_recorder.js` | «Запись для меня»: сценарий по метке и WAV |
| `06_side_pick.js` | выбор стороны: какой канал громче у микрофона |
| `07_calibration.js` | калибровка по шагам и её расчёт `calCompute` |
| `08_wiring.js` | кнопки, быстрый старт, переключатель беззвучного режима |
| `09_game_ui_log.js` | игра: цикл, рисование, звуки, меню, журнал партии |

### 2.1. Зонд

- Частота дискретизации 48 кГц, период зонда N = 512 отсчётов, то есть спектральные линии через 93,75 Гц.
- Полоса — бины 196–218, **18,38–20,44 кГц, 23 частоты** (`F_LO = 18300` в `04_audio_engine.js` и `Math.ceil(18300/df)` в `02_dsp.js` — менять только вместе).
- Равные амплитуды, фазы Шрёдера π·q²/M, где q — номер частоты в полосе, M — число частот. Нормировка на пик 0,9.
- Играется зацикленным `AudioBufferSource` ровно одного периода, поэтому строго периодичен.
- Играет только один стереоканал — тот, чей динамик громче у микрофона (`pickChannel`). В альбомной ориентации это нижний динамик, рядом с микрофоном; на телефоне пользователя это правый канал.
- **Автоуровень** (`autoLevel`): приложение меряет сигнал/шум своего зонда и подгоняет уровень к цели 48 дБ, в пределах 0,015–0,3. Громкость зонда в комнате поэтому почти не зависит от громкости телефона. Если нужно больше, чем 0,3, — предупреждение «прибавь громкость»; если сигнал/шум ниже 30 дБ — зонд выключается, «зонда почти не слышно».
- **Сигнал/шум** (`probeSNR`): 8 периодов подряд, 4096 отсчётов, ДПФ по полосе. Зонд строго периодичен, поэтому ложится ровно в каждую 8-ю линию, а шум размазан по всем. Сравнение этих двух дают сигнал/шум в полосе. Оценка строже внешней на 6–14 дБ, потому что считает помехой и непериодическую дрожь прямого сигнала.

### 2.2. Приём

- Микрофон: `getUserMedia` с выключенными `echoCancellation`, `noiseSuppression`, `autoGainControl`, моно.
- **Кадры берутся только из AudioWorklet** — непрерывный поток, отсчёт к отсчёту. Проверено на записях: прямой сигнал за 15 с сдвигается по фазе всего на 0,42 рад, проскальзываний входа относительно выхода нет. Поэтому никакой привязки кадров не нужно. `AnalyserNode` отдаёт окно в произвольном месте потока — ровно из-за этого проваливались ранние версии (раздел 4).
- Все режимы — запись, калибровка, игра — видят одни и те же кадры через `onFrame`, поэтому записи для разбора точно отражают то, что видела игра.

### 2.3. Обработка `DSP2`

По каждому кадру из 512 отсчётов:

1. **Импульсная характеристика канала**: ДПФ только по бинам зонда (таблицы cos/sin), умножение на сопряжённые фазы зонда, обратное преобразование в «полосу у нуля» — для нужных отсчётов задержки.
2. **Старт, первые 30 кадров**: мощности по всем 512 отсчётам задержки. Максимум — прямой сигнал `d0`. Выраженность пика над медианой должна быть не меньше 12 дБ, иначе `noProbe` — зонда не слышно. Также запоминается `dref` — мощность прямого сигнала.
3. **Полоса руки**: отсчёты задержки от 30 до 300 мм после `d0`, мм на отсчёт = 343/48000/2·1000 = 3,57.
4. **Усреднение пары соседних кадров** убирает чередование с частотой 46,9 Гц: iOS обрабатывает звук буферами по 1024 отсчёта, и соседние периоды зонда попадают в разные половины буфера.
5. **Фон пустой комнаты**: среднее за 40 кадров. Дальше подстраивается с τ = 2 с **только когда руки нет**, иначе впитывал бы неподвижную ладонь.
6. **Быстрая часть**: разность кадров через 4 — неподвижное вычитается само. Скорость — по методу пар: угол Σ g(t)·g*(t−1) по всей полосе, умноженный на λ/4π. Все части ладони движутся с одной скоростью, поэтому их вклады складываются согласно даже при спутанных фазах. Складывается в смещение, только если энергия движения выше −30 дБ относительно прямого (`T_INT`).
7. **Абсолютная часть**: центр тяжести |h − фон|² по полосе руки, это дальность в мм. По калибровке: высота = k·дальность + o. Затем медиана по 15 кадрам.
8. **Слияние**: итог += s·скорость. Расхождение «медиана абсолютной − итог» сглаживается с τ = 3 с (`eAvg`, `TE`). К абсолютной подтягивается с τ = 1,5 с только та часть сглаженного расхождения, что выходит за **мёртвую зону ±5 мм**. Абсолютная часть работает как ограничитель ухода, а не как вторая рука на штурвале — иначе в игре появлялась «резинка». С 24.09 вечера (игра v0.11) обе постоянные времени делятся на 1+(e/12)², где e — сглаженное расхождение в мм: при быстрых размашистых взмахах быстрая часть уплывала на 60–90 мм, и корабль «прилипал» к краю (партия sonaroids_game_20260924_2001). На шести журналах игры время с уходом центра больше 40 мм упало примерно вдвое, дрожание итога не изменилось; на записях с меткой форма та же (кроме 1126 с негодной калибровкой).
   С 24.09 ночи (игра v0.17) отклик каждого кадра **нормируется на прямой сигнал** — его комплексное усиление (уровень и фаза) сглаживается с шагом 0,03 и учится только в тихой пустой комнате (`!present && Es<Q_FLOOR`), как уровень пустоты. Причина — OnePlus 13: усиление тракта «динамик→микрофон» там плавает на 2–3 дБ за секунды, а хвост прямого сигнала у телефона сильный (−27 дБ от прямого против −55 на iPhone), и остаток пустой комнаты был −10 дБ вместо −30. Учить усиление при руке нельзя: на iPhone эхо ладони сравнимо с прямым и просачивается в прямой отсчёт — высота портилась (1128: медиана против метки 13 → 39 мм). Итог на записях с меткой: OnePlus 2227 форма 0.730 → 0.994, 2228 −0.05 → 0.930; iPhone без изменений.
   **Низ у стола** (с 25.09, игра v0.23): ниже середины (`x<100`) абсолютная часть тянет вверх без ускорения `kq` и с мёртвой зоной ±15 мм (`DEADB_UP`) вместо ±5: при ладони на 4–5 см центр эха уезжает вверх на 25–40 мм. Запись с линейкой 11:09 (4–12 см, «8–12–4–8»): форма 0.826 → 0.911, размах 56 → 66% от настоящего, дрожь удержания 6.9 → 4.1 мм; 11:26: 0.628 → 0.895; остальные записи iPhone те же или лучше. В партиях корабль опускается немного ниже (5-й процентиль на 2–18 мм). Проверено и отброшено: окно разности L=3 и L=2 вместо 4 (меньше задержка, но на удержании уход до 20 мм). И то же правило для верха (выше середины тянуть вниз без ускорения): на записях с меткой так же или лучше, но на старых партиях итог уходил вверх до 11 см (1904, 1938) — ровно тот «прилип к краю», ради которого ускорение вводилось.
   **Выравнивание полосы** (с 25.09, игра v0.20): на OnePlus и Redmi зонд у микрофона к 20 кГц слабее на 20–33 дБ, чем на 18,4 (iPhone — ~11 дБ); верхняя половина полосы пропадала, отклик расплывался. На старте (30 кадров, пустая комната) меряется уровень каждого тона; если перепад больше 16 дБ (`EQ_ON`), каждый тон дальше делится на свой уровень, но не больше чем в 10 раз (`EQ_MAX`). На iPhone перепад 9,5–13 дБ — выравнивание не включается, всё как было. OnePlus по метке: 22:27 форма 0.994 → 0.996, неподвижная рука видна 15% → 100%; 22:28 0.930 → 0.974, против метки 109 → 42 мм; 23:40 0.942 → 0.967, 80 → 13 мм. Redmi у камеры (00:24): 0.735 → 0.689 по форме, 38 → 29 мм против метки. Минус: на OnePlus рука после ухода иногда «остаётся». В `info()` — `eq`, `eq_db`.
   **Провалы входа** (с 24.09 ночи, игра v0.18): Android иногда вставляет во вход кусок тишины — в записи OnePlus 23:40 это 1920 нулей подряд. Весь отклик сдвигается по задержке на 1920 mod 512 = 384 отсчёта, прямой сигнал «уезжает» с `d0`, остаток пустой комнаты становится +10 дБ, и рука «видна» до конца. Теперь кадр с 48 нулями подряд пропускается (разности начинаются заново), а если прямой отсчёт ниже −10 дБ ~0,1 с — пик ищется по всем задержкам (не чаще раза в 0,5 с) и при силе не ниже −6 дБ `d0` переезжает туда; усиление `gN` берётся заново, потому что сдвиг поворачивает и фазу. Запись 23:40: форма 0.751 → 0.942. Счётчики — `info().drops`, `info().relocks`.
   Проверено и отброшено: переучивать усиление при руке на ступеньках уровня больше 6 дБ (в журнале OnePlus 2144 ступенька −20 дБ, но это не изменение усиления; на iPhone это чуть портило игры) и выход руки только без движения (рука «прилипает», форма хуже).
   До 24.09 тянуло мгновенное расхождение с зоной ±10 мм. Но у краёв абсолютная часть сжата: в партиях с новым зондом (10:26, 11:59) внизу поля «абсолютная − итог» было +6…+12 мм, вверху −15…−20. Поэтому корабль оттягивало к середине — жалоба «ладонь на столе, а корабль не внизу». Сглаженное расхождение у краёв почти не меняется, а общий уход по-прежнему ловит. Записи по метке (самокалибровка, по форме / разброс):
   - 22:51 — 0,973 → 0,978 / 6,3 → 5,3 мм;
   - 10:20 — 0,940 → 0,954 / 9,0 → 6,9;
   - 11:28 — 0,983 → 0,980 / 5,8 → 4,2;
   - остальные в пределах ±0,01.
   С физической калибровкой форма на 11:26 выросла с 0,894 до 0,968.
9. **Присутствие руки**:
   - появление — по движению (сглаженная энергия движения выше −16 дБ) или по резкому росту эха на 15 дБ над уровнем пустой комнаты в течение 4 кадров; вход по эху разрешён только после секунды разогрева;
   - **уровень пустой комнаты учится только на тихих кадрах** — сглаженная энергия движения ниже −28 дБ (`Q_FLOOR`). С 24.09: раньше он учился на всех кадрах без руки, и если ладонь уже шевелилась рядом при запуске обработки (пустая комната в калибровке, быстрый старт), он за секунду выучивал её эхо как «пустоту». Дальше неподвижная рука переставала быть видна: движение — вход, замерла — через 0,3 с уход, и так по кругу. Это баг «рука видна рывками»;
   - рука остаётся, пока её эхо выше пустой комнаты на 10 дБ, — даже неподвижная и в «тихой» позе;
   - уход — эхо 0,3 с ниже этого порога **или** эхо упало на 18 дБ ниже своего уровня с рукой (`ePres`) и не выше пустоты + 15 дБ; после ухода 0,7 с новый вход не принимается. Второй признак нужен, потому что с «чистым» уровнем пустой комнаты фон к концу удержания устаревает и эхо после ухода руки не опускается до пустоты;
   - в выходе обработки есть `floor` (уровень пустой комнаты, `null` — ещё не выучен), `Em` (сглаженная энергия движения) и `why` (причина последнего входа или ухода) — для диагностики и журнала настройки.
   Сравнивать уход с пиком эха напрямую нельзя: эхо ладони меняется от позы на 10 дБ, и это давало ложные уходы на удержании; отсюда запас 18 дБ.
   **Проверка исправления:** стенд `startmid.js` запускает обработку посреди «Записи для меня», когда ладонь уже рядом. До: рука видна 28–30% времени движения, 6–9 ложных уходов за запись. После: 90–100%, 0–1. Журналы партий, прогнанные с фоном по началу журнала (ладонь уже на месте): 85,5% и 36,6% → 100%. На обычных записях всё прежнее, кроме sonar1h_20260923_2251: по форме 0,985 → 0,973, разброс 3,7 → 6,3 мм, но против метки медиана 7,5 → 4,5 мм — рука теперь замечается на кадр раньше, и начальная высота берётся из другого кадра. Неподвижная ладонь, стоявшая рядом ещё при запуске, остаётся невидимой, пока не шевельнётся — она часть «пустой комнаты».
10. **Пропажа зонда**: прямой сигнал ниже `dref` на 20 дБ дольше секунды — `lost`. Игра выключает зонд и пишет «НЕТ ЗОНДА». Это случай наушников, Bluetooth и машины: звук уходит туда, и там он пищит.

Параметры по умолчанию: `T_ON = −16`, `T_INT = −30`, `HOLD_S = 1,5`, `REFR_S = 0,7`, `TAU_BG = 2`, `TAU = 1,5`, `TE = 3`, `ABS_MED = 15`, `DEADB = 5`, окно разности `L = 4`.

### 2.4. Подготовка без калибровки и центровка (с 24.09)

**Пошаговой калибровки больше нет.** Пользователь жаловался: «стоит чуть плохо пройти калибровку — управлять сложнее». Журналы настройки 11:54 и 11:57 это подтвердили. «Низко» и «высоко» различались по дальности всего на 43–56 мм, поэтому поле экрана сжалось до 55 мм хода ладони против 88–120 мм в удачных партиях. А на 11:57 покачивание не прошло проверку согласия (0,54), и масштаб быстрой части взялся запасной, s = k = 2,35, на треть больше верного. По журналам партий ход ладони на весь экран менялся от раза к разу в 2,2 раза (55–120 мм).

**Что вместо неё — физика.** Быстрая часть — это смещение по фазе, то есть почти миллиметры пути. По всем шести записям с меткой:

| запись | мм метки на ед. быстрой | дальность на ед. быстрой |
|---|---|---|
| 22:51 / 21:10 / 09:34 / 10:20 / 11:26 / 11:28 | 0,82 / 0,84 / 0,87 / 0,88 / 1,01 / 0,95 | 0,71 / 0,91 / 0,88 / 0,81 / 0,61 / 0,73 |

По покачиваниям в журналах настройки дальность на ед. быстрой — 0,71–0,78. Отсюда постоянные `PHYS_CAL = {k: 1,17, s: 0,9}`: s — мм высоты на единицу быстрой части, k = s/0,77 — мм высоты на мм дальности. С ними размах движения на всех записях — 91–99% от метки. Самокалибровка по самой записи давала 88–184%, при той же «форме».

**Середина поля ставится сама** (`DSP2.recenter`). Берётся медиана дальности и итога за последнюю секунду с рукой: o = 100 − k·r0, а итог сдвигается так, чтобы медиана встала на 100. Движение при этом не теряется. Когда это происходит:
- через 0,8 с после первого появления руки (`DSP2.set('autocenter',1)`, по умолчанию выключено — инструменты разбора работают как раньше);
- ~~в конце каждого отсчёта~~ — убрано в тот же день: пользователя напрягало, что сразу приходится держать ладонь «в середине», а вдруг она неудобная.

**Подстройка по взмахам перед стартом** (`autoTune` в `09_game_ui_log.js`, по предложению пользователя). Пока игра ждёт «Старт» или «Ещё раз», корабль ходит за ладонью, а подсказка просит: «помаши ладонью вверх-вниз, примерно 5–15 см над столом — корабль подстроится под твой размах».
- Берутся высоты за последние 6 с, из них 5-й и 95-й процентили — это помаханный диапазон.
- Раз в 0,25 с середина и ход на весь экран подтягиваются на треть к цели. **Помаханный диапазон ложится на 10–90% экрана** — с запасом с обеих сторон.
- Вариант «ладонь на столе — корабль внизу» (низ на 3%) продержался одну версию. Пользователь его отверг: у стола сонар подлагивает и ошибается, игроку захочется поправить ещё ниже — а там уже стол. **Рабочий диапазон ладони — 5–15 см над столом**: удобно играть, и сонару он лучше всего (записи по метке сняты как раз в нём).
- Когда диапазон пойман (размах ≥ 3 см за ≥ 1,5 с), у индикатора руки появляются две зелёные отметки и надпись «диапазон N см пойман — можно жать «Старт»».
- Если ладонью не машут, к середине подтягивается только медиана.
- С отсчёта до конца партии всё заморожено.
- Сдвиг шкалы — `DSP2.shift(d)`: сдвигает o, итог и буферы. Каждый шаг пишется в журнал настройки событием `подстройка`, повторный прогон их применяет и совпадает с телефоном до 0,1 мм.
- Ход на весь экран подбирается, пока в меню «Подбирать по взмахам: да». Если тронуть ползунок, подбор выключается и ход ставится вручную. Оба значения запоминаются: `sonar_field_mm`, `sonar_field_auto`.

**Экран растянут ниже середины в 1,7 раза** (`ASYM`, `fracOf`). По всем шести записям с меткой итог в нижней половине хода (5–10 см) идёт на ~0,85 мм за мм, в верхней (10–15 см) — на ~1,45: у стола сонар видит движение слабее. С растяжкой при метке 50/75/100/125/150 мм корабль в среднем на 13/39/45/60/89% экрана, без неё — 12/32/36/52/88%; линейно было бы 10/30/50/70/90. Стенд — `tools/screen_linearity.js`.

**Поле экрана** — «Ход ладони на весь экран» в меню: 5–15 см, по умолчанию 10 см (рабочий диапазон 5–15 см), дальше подбирается по взмахам. Высоты в миллиметрах, середина — 100.

**Подготовка** (`quickStart` в `07_calibration.js`) идёт сама: выбор стороны, автоуровень, пустая комната — «Убери руку», около 2 с. Потом сразу игра. Если зонда не слышно — кнопка «Ещё раз». В меню «Заново послушать комнату».

Старый расчёт `calCompute` живёт только в `tools/common.js`: им `eval_recording.js` и `synth_probe.js` по-прежнему оценивают записи с меткой (самокалибровка по пикам синусоиды).

**Проверка на журналах** (`replay_game.js --phys` прогоняет старый журнал по новой схеме). Шум итога в долях экрана:
- 11:59 (калибровка k = 2,35): 3,2% → 1,6%;
- 00:06 и 10:26 (удачные калибровки): почти как было — 1,4% → 1,3–1,8%.

Согласие быстрой и абсолютной частей не изменилось. Стенд `test_center.js` на синтетике: середина после появления руки — 100,0; повторная центровка на удержании сдвигает на 0,4 мм; размах 89% при ожидаемых 90%.

### 2.5. Игра

- Состояния: ожидание (корабль уже ходит за рукой) → «Старт» → отсчёт 3 с → полёт → проигрыш → «Ещё раз» → отсчёт. **Пауз нет.** Без руки корабль стоит на месте.
- Сложность — таблица `DIFF` в `03_game_core.js`: стартовая скорость, ускорение, размер астероидов, частота появления, с какого уровня парами, щедрость столкновений, жизни. По умолчанию «легко»: 5 жизней.
- Рекорд — отдельно для каждой сложности, `localStorage` с ключом `sonar_asteroids_best_<сложность>`.
- Звуки идут через шину: компрессор, ограничитель и **три фильтра нижних частот по 6 кГц**. По расчёту даже громкий квадратный сигнал попадает в полосу зонда на 114–133 дБ ниже самого зонда. Ноты 880–1570 Гц — там телефонный динамик громкий.
- Интерфейс: надписи по центру и внутри безопасной зоны экрана (вырез камеры читается через `env(safe-area-inset-*)`). Кнопка меню опущена от края. Перезагрузка есть на главном экране, в подготовке и в меню.
- **С 24.09 весь интерфейс альбомный и в один экран**, без прокрутки. Экраны раскладываются в две колонки — текст слева, кнопки справа; меню игры — в три колонки. Базовый шрифт растёт с высотой экрана: `html{font-size:clamp(10px,3.6vh,17px)}`, при высоте 390 px — 14 px. Все размеры заданы в rem. Если экран или меню всё же не влезает, `fitScreen()` уменьшает шрифт по 0,5 px. Её вызывают `show()`, `calText()`, открытие меню и поворот экрана.
- В портретной ориентации поверх всего — «Поверни телефон горизонтально» (чистый CSS, `@media (orientation:portrait)`). Экран `orient` теперь просит только положить телефон.
- Масштабирование Safari отключено тремя способами: `maximum-scale=1, user-scalable=no` в viewport (iOS его частично игнорирует); `touch-action:manipulation` снимает двойной тап; события `gesture*` и `touchmove` двумя пальцами гасятся. Двойной тап вне кнопок гасится по `touchend`. Страница зафиксирована (`position:fixed; overflow:hidden; overscroll-behavior:none`) — не тянется и не пружинит.
- **Кнопки — со стороны свободной руки** (с 24.09, по просьбе пользователя: жмёт левой, правая занята игрой). Рука справа — колонка кнопок на всех экранах слева. «Меню» слева вверху; «Старт» и «Ещё раз» слева внизу, «Сохранить журнал» над ними. Колонка «Продолжить» в меню — крайняя левая, живая полоска подготовки — со стороны руки. Если `pickChannel` выбрал левую руку, всё зеркально: класс `body.hand-left`, функция `handSide()`. Сторона запоминается в `localStorage` (`sonar_hand`), чтобы главный экран сразу открывался правильно. До первого выбора стороны считается, что рука справа. Индикатор руки на холсте игры рисуется тоже со стороны руки.
- До 24.09 из-за лишней скобки в `calc()` правило `bottom` у игровых кнопок не работало, и они оказывались вверху.
- Проверка: `tools/tests/test_layout.py` (Chromium через playwright). Все экраны и меню на размерах 568×320, 667×375, 750×390 (844×390 за вычетом выреза), 844×390, 932×430 и 1002×462 — ничего не вылезает, прокрутки нет; портрет — только просьба повернуть; кнопки со стороны свободной руки для обеих сторон. Снимки — `tools/out/layout_*.png`.
- Событие кнопки «Старт» отдаётся в следующем кадре игры (`g.pending`). Раньше оно стиралось очисткой событий в начале кадра, и журнал не начинался.

### 2.6. Журнал партии

Включён по умолчанию, пишется от отсчёта до проигрыша; длинная партия хранит последние 150 с. Сохраняется кнопкой после проигрыша через меню «Поделиться».

Формат — один WAV:
- `fmt` — PCM16, моно, 48 кГц; полная шкала = 1/4 входа (`meta.pcm.full_scale`). 16 бит против 32 меняют высоту в среднем на 0,03 мм;
- `LIST/INFO/ICMT` — метаданные JSON: полоса, канал, уровень и запас зонда, калибровка, сложность, поле, звуки, первый кадр, зашкалы, разрывы, UA;
- `glog` — JSON с тремя массивами:
  - `dsp` — по кадрам обработки: [кадр, рука 0/1, высота, абсолютная, дальность, быстрая, энергия движения, эхо];
  - `render` — по кадрам игры: [кадр, мс, рука 0…1 или −1, корабль y/H, состояние, жизни, счёт, уровень, астероиды [x/H, y/H, r/H]];
  - `events` — [кадр, событие, корабль y/H];
- `data` — звук.

Разбор — `tools/game_log.py`.

### 2.6а. Журнал настройки

Пишется с запуска обработки — пустая комната в калибровке или быстрый старт — через все шаги калибровки и ожидание «Старта» и дальше в игру, до 120 с. Сохраняется кнопкой «Сохранить журнал настройки» на экране калибровки и в меню игры, файл `sonar_setup_<дата>.wav`. Формат как у журнала партии (PCM16, `ICMT`, `glog`), `kind: 'setup-log'`:
- `dsp` — [кадр, рука, высота, абсолютная, дальность, быстрая, энергия движения, эхо, уровень пустой комнаты, сглаженная энергия движения];
- `events` — старт, кнопки «Готов», записанные шаги с долей кадров с рукой и дальностью, итог калибровки, появления и уходы руки с причиной, отсчёт;
- в метаданных — калибровка до и после, зонд, выраженность прямого сигнала.
Так как журнал начинается с запуска обработки, повторный прогон повторяет телефон: присутствие совпадает в 100% кадров, высота — до 1,6 мм (16 бит). Разбор: `tools/setup_log.py` (события и лента по времени, счётчик «рывков»), `tools/replay_game.js` (повтор, в том числе с правками `--patch`).

Строка диагностики: на экране калибровки всегда, в игре — по кнопке «Диагностика на экране» в меню. Показывает, видна ли рука и почему, эхо над уровнем пустой комнаты и энергию движения.

Меню игры с 24.09 прокручивается: раньше в альбомной ориентации оно было выше экрана, и «Продолжить» с выбором сложности уходили за верхний край.

### 2.7. «Запись для меня»

16 с по метке у края экрана со стороны руки: пусто 0–3 с, ладонь на 100 мм 3–5, синусоида 100 ± 50 мм с периодом 6 с на 5–11, неподвижно на 100 мм 11–14, рука убрана 14–16. Формат — WAV float32 моно 48 кГц и метаданные JSON в `ICMT`: сценарий, метки начала фаз в отсчётах, канал, уровень и запас зонда, полоса. Разбор — `tools/eval_recording.js`.

### 2.7а. Длинная запись (с 26.09)

Кнопка «Длинная запись (1,5 мин)»: пустая комната 3 с, ладонь на 10 см, потом 4 круга по 22 с — «веди за меткой» 18 с (100 ± 50 мм, период 6 с) и «замри» 4 с, в конце «убери руку»; 96 с, файл `sonarlong_*.wav` (float32, ~18 МБ). Разбор — `tools/eval_long.js`: движок как в игре (калибровка `PHYS_CAL`, центровка), по каждому кругу — согласие с меткой, масштаб, сдвиг, удержание, и отдельно согласие с меткой дальности эха и быстрой части; уход — от 1-го круга к 4-му. `--set`/`--patch` — варианты обработки, `--synth [--drift]` — самопроверка (с `--drift` отражение комнаты уезжает на ~0,9 мм/с).

Зачем: игра с телефоном в руке (ладонь ребром у торца с разъёмом, 5–15 см; ближе — корабль ниже). Запись по метке 26.09 10:41 — лучшая за всё время: по форме 0.997, разброс 1,2 мм, масштаб при `PHYS_CAL` ровно 1,00, дальность эха с меткой 0.96. Но в партии 10:29 согласие быстрой части и дальности +0.93 в первые 10 с и ~0 уже с 20 с до конца (на столе ~0.8 всю партию): пустая комната обновляется только без руки (`if(!present)`), а в руке ладонь у торца всегда и телефон шевелится. Проба — фон учится и при руке с τ 5–10 с: согласие на журнале 10:29 0.01 → 0.25, на столе без изменений. Вероятно, так же устаревает `gN` (прямой сигнал учится только в тихой пустой комнате).

### 2.8. Прочее

- Веб-приложение с домашнего экрана: мета-теги `apple-mobile-web-app-*` и иконка. Если открыто просто в Safari, на главном экране есть подсказка, как добавить. Микрофон в режиме домашнего экрана работает, iOS может спрашивать разрешение при каждом запуске.
- Переключатель «Беззвучный режим телефона» — эксперимент с сессией `play-and-record`. На телефоне пользователя не сработал; при отказе iOS приложение само возвращается к обычному режиму.

## 3. iPhone и Safari: что выяснено

Телефон пользователя — iPhone, в UA `iPhone OS 18_7`, версия Safari 27 (iOS замораживает версию ОС в UA).

- **Один микрофон.** `channelCount: 2` даёт только один канал — проверено отдельным тестом. Две руки поэтому не разделяются.
- **AudioWorklet даёт непрерывный вход,** синхронный с выходом по отсчётам. `AnalyserNode` — окно в случайном месте, для когерентной обработки не годится.
- **Чередование 46,9 Hz** между соседними периодами зонда — след буферов iOS по 1024 отсчёта; лечится усреднением пар.
- **Непериодическая дрожь прямого сигнала** около −29…−32 дБ от кадра к кадру — у самого телефона, есть всегда.
- **Микрофон режет выше ~21 кГц;** рабочая полоса — до 20,5 кГц.
- **Беззвучный режим глушит Web Audio:** Safari кладёт страницу со звуковым движком в «фоновую» сессию. Сессия `playback` снимает это, но **запрещает микрофон** — ошибка «audio session category not compatible», так сломалась одна из версий. Сессия `play-and-record` на телефоне пользователя не помогла. Итог: беззвучный режим надо выключать.
- **Системную громкость страница не читает и не ставит.** Регулируем только свой зонд — автоуровень.
- **Полноэкранный режим элемента** (`requestFullscreen`) на iPhone не работает — только через домашний экран.
- **Bluetooth, наушники, машина** уводят звук туда: зонд там пищит и механика не работает — отсюда выключение зонда.
- **Сторона руки.** До 0.17 и снова с 0.18 — канал, чей зонд громче у микрофона. 24.09 ночью на Redmi: «громкий канал» 9 раз из 10 показывал на конец с фронтальной камерой, и рука видна именно там, у разъёма — не видна совсем (видимо, рабочий микрофон у Redmi вверху). Лаба пишет, какой это конец: у разъёма или у камеры (по `screen.orientation.angle`). Игра с 0.18 учит конец телефона сама (раздел 2 в `docs/design.md`).
- **Первое чтение большого загруженного файла** с диска в песочнице разбора бывает медленным, до минуты; перед разбором стоит «прогреть» файл через `dd`.

## 4. Что пробовали и почему не пошло

| подход | результат | почему |
|---|---|---|
| Дальность ступенчатой гребёнкой, пик и центр тяжести | 6–22 см, прыгает | полоса 1,8 кГц даёт разрешение 9,5–14 см на всю зону в 16 см; оборот шкалы из-за задержки системы |
| Амплитуда эха | десятки дБ от миллиметровых сдвигов | спекл: при λ = 18 мм части ладони складываются то в фазе, то в противофазе |
| Фаза сильнейшего тона | скачки на ±100 мм | переключение между счётчиками разных тонов |
| Фаза по медиане тонов, AudioWorklet-гребёнка | «1–2 ноты» | фаза суммы тянется за самым сильным отражателем |
| Ударные по доплеру и по акселерометру | ненадёжно, «хрень» | не та задача для этого железа и пользователя |
| Импульсный зонд через `AnalyserNode` | промах на 2,51 отсчёта | фаза повторяется каждые N/kc отсчётов, привязка к плоской вершине неоднозначна; окно в случайном месте потока |
| Две руки на двух динамиках (чётные и нечётные бины) | правая рука глушит левую на 9–21 дБ | один микрофон у правого края; предплечье правой руки лежит в дальности левой; вычитание по опоре не помогло |
| Стерео-микрофон | один канал | Safari отдаёт моно |
| Начальная высота по медиане при входе руки | хуже на всех 4 записях | в момент входа медиана тянет к замерам до прихода руки |
| Поднятый порог интегрирования, −22 дБ | терялись медленные движения | энергия движения растёт как квадрат скорости — это порог по скорости |
| Сессия `playback` против беззвучного | микрофон запрещён | категория только для вывода |

**Что сработало и почему:** когерентная импульсная характеристика из непрерывного потока AudioWorklet плюс скорость методом пар по всей полосе после разности кадров. Абсолютная высота мерится, только когда ладонь **сбоку** от телефона: над экраном рука сидит в хвосте прямого сигнала и в отражениях корпуса.

Новый зонд по одной записи чуть хуже. Цель запаса после этого поднята с 44 до 48 дБ. **Проверка 24.09 (записи 11:26 и 11:28): точность вернулась к уровню старого зонда** — 0,983 по форме в обеих. Но запись с 44,7 дБ не хуже записи с 47,8 дБ, так что провал 10:20 — скорее разовый, чем от запаса; цель 48 дБ оставлена. Уровень зонда при 47,8 дБ был 0,147 — не громче, чем в 10:20 (0,157): в комнате было тише. В 11:26 после «убери руку» эхо осталось на ~20 дБ выше пустой комнаты с центром около 23 см — рядом что-то осталось (скорее рука, отведённая недалеко); прямой сигнал за запись стабилен (фаза ±0,02 рад), дрейф фона не виноват. Абсолютная часть на всех записях ходит на 0,6–0,9 мм на миллиметр настоящего движения (наклон дальности на быструю часть); калибровка это поглощает.

### 5.2. Партии

| партия | зонд | шум итога | крупные скачки | шум абсолютной | согласие частей |
|---|---|---|---|---|---|
| 23.09 23:50 | старый, без мёртвой зоны | 2,40 мм | 4,5 мм | 24,0 мм | 0,44 |
| 24.09 00:06 | старый | 1,50 мм | 3,2 мм | 14,6 мм | 0,54 |
| 24.09 10:26 | новый, уровень 0,101, 43 дБ | 1,58 мм | 2,4 мм | 20,1 мм | 0,48 |
| 24.09 11:59 | калибровка k = s = 2,35 (неудачная) | 3,52 ед. (3,2% экрана) | 8,1 | 30,6 | 0,29 |
| 24.09 13:08 | **без калибровки, подстройка по взмахам**, ход 7,6 см | 1,58 мм (2,1% экрана) | 2,8 мм | 15,8 мм | **0,59** |

Рука видна 100% во всех партиях, удары — игровые промахи, а не сбои.
Партия 13:08 — первая по новой схеме. Пользователь: «уже прям хорошо». Счёт 11 057 на лёгкой, 23-й уровень — вровень с лучшей партией 23.09 (11 086). Первые ~110 с в журнале — ни одного удара.

Во второй половине партии корабль заметную часть времени шёл по самому верху экрана: у верхнего края 11% времени, на отдельных отрезках 20–27%. **Это нарочно:** пользователь летел поверху, потому что там меньше камней. Сбоя прибора нет: дальность растёт вместе с итогом, «абс − итог» в ±20 мм.

Почему у края безопаснее. Центры камней разбросаны по высоте от r до H − r. Корабль у края прижат к полю в 8% от него. Камень может задеть его только с одной стороны, поэтому риск столкновения там примерно вдвое ниже, чем в середине.

### 5.3. Запас и полоса

- Механике нужно около 30 дБ в полосе: работает до ~24 дБ, ломается на ~14 дБ (ложные срабатывания в пустой комнате).
- Срез полосы до 18,3 кГц на старых записях не менял точность; до 18,8 кГц одна запись заметно теряла.
- Задержка обработки около 40–50 мс; слияние добавляет к быстрой части ~11 мс; появление руки замечается через 0,2–0,3 с после роста эха.
- Виртуальный игрок с человеческой рукой держится: «легко» 127–151 с, «средне» 66–72, «сложно» 43–51. Пользователь набрал 5316 на средней.

## 6. Методика проверки

Главное правило, выученное дорого: **ничего не отдавать пользователю без проверки на его настоящих записях** — модели трижды оказывались оптимистичнее железа. Порядок:

1. **Настоящие записи** — `eval_recording.js` и `game_log.py`. Для записей со старым зондом движок автоматически переключается на полосу от 17 750 Гц по метаданным. `eval_recording.js --phys` оценивает с калибровкой как в игре (`PHYS_CAL`) — так надо смотреть записи, где ладонь ходила не по метке 100 ± 50 мм (11:09, 4–12 см): самокалибровка там ломается. `game_log.py` читает журналы и лабы, и самой игры (`sonaroids_game_*`). Всё сразу по папке — `sh tools/run_data.sh папка`.
2. **Синтетика с текущим зондом** — `synth_probe.js`: проверка, что генератор зонда и анализ совпадают. Это обязательно при любом изменении зонда — старые записи с новым зондом не читаются.
   Для опытов с обработкой: `eval_variant.js` (записи с меткой, `--set`/`--patch`) и `replay_game.js` (журналы партий). Повторный прогон журнала повторяет шум итога телефона (2,40 / 1,49 / 1,58 мм против 2,40 / 1,51 / 1,58), а шум абсолютной — лишь примерно: пустой комнаты в журнале нет, фон оценивается средним за партию. Варианты сравнивать с прогоном без изменений, а не с цифрами телефона.
3. **Стенды страницы** — `tools/tests/`: код самого приложения с поддельными DOM, холстом, часами и таймерами. Калибровка, игра, журнал партии, журнал настройки (с повторным прогоном файла), пропажа зонда, автоуровень, запуск микрофона.
   Подготовка, центровка и подстройка по взмахам — `test_quick_start.js`, `test_center.js`, `test_autotune.js` (пошаговую калибровку тестировал `test_calibration.js`, удалён вместе с ней).
   «Плохой старт» — `startmid.js`: обработка запускается посреди «Записи для меня», когда ладонь уже рядом; печатает долю кадров с рукой по фазам и число ложных уходов.
4. Перед выдачей: `python3 build.py --check` и `sh tools/run_all.sh`.

**Ловушки, в которые уже попадали:**
- стенды с поддельными часами должны пропускать отложенные продолжения промисов между кадрами (`await null`), иначе калибровка «застревает»;
- поддельный холст должен уметь `measureText`;
- не читать старый промежуточный файл вместо нового — однажды из-за оборванного скрипта старый журнал выдавался за новый. Проверять дату в метаданных;
- при сравнении с меткой помнить, что человек сам отстаёт и промахивается — судить по «форме», а не по сырой ошибке;
- медиана по окну не годится там, где в окно попадают замеры до события (вход руки).

## 7. Как собрать, проверить и выложить

0. В репозитории лаба лежит в папке `lab/` — всё уже по местам.
1. Править части в `src/`.

## 8а. Заметки к игре «с нуля»

Пользователь собирается делать саму игру заново, отдельными файлами. Лаба остаётся стендом механики. Что учесть:
- **ближе к середине экрана — больше очков.** Иначе выгодно прижиматься к краю, где камни достают только с одной стороны (партия 13:08). Как вариант — множитель очков по высоте корабля; также камни, которые чаще идут у краёв;
- рабочий диапазон ладони — 5–15 см над столом: сонару он лучше всего, играть удобно;
- без калибровки: пустая комната, потом подстройка по взмахам перед стартом;
- кнопки — со стороны свободной руки;
- альбомный экран, всё в один экран, без масштабирования Safari.
